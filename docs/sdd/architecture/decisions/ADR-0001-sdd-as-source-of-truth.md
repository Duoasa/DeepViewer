# ADR-0001：使用仓库内 SDD 作为开发事实来源

## 背景

DeepViewer 将在快速变化的 DeepSeek Harness 上进行 UI 和产品定制。只有任务列表而缺少稳定的需求、架构和验证记录，会让实现偏离产品目标，也会增加上游同步时的判断成本。

## 决策

DeepViewer 在 `docs/sdd/` 中维护版本化的 Markdown 规格。每个非平凡变更使用唯一 `DV-NNNN` 目录，包含需求、设计、任务和验证四个文件。长期架构决策使用 ADR，产品愿景和原则作为跨规格基线。

规格与代码在同一仓库、同一变更中演进。批准规格不是永久冻结；行为改变时必须先更新规格及验收条件，再更新实现。

## 后果

### 正面

- 产品意图、设计、任务和证据可以双向追踪。
- 人和编码 Agent 使用同一事实来源。
- 上游变化可以根据已记录的产品边界进行取舍。
- 评审能区分需求变化、设计变化和实现缺陷。

### 代价与风险

- 非平凡变更需要额外的文档维护。
- 规格可能与代码失去同步，因此完成定义必须检查二者一致性。
- 过度详细的模板会降低使用率，因此只要求对决策有价值的内容。

## 备选方案

- 只使用 GitHub Issues：适合排期，但不足以保存完整设计与验证映射。
- 只使用代码和测试：能描述当前行为，但难以保存产品意图和被否决方案。
- 使用外部文档平台：协作能力强，但离线性、版本一致性和 Agent 可访问性较差。

## 后续行动

- 所有非平凡功能从 `docs/sdd/specs/_template/` 开始。
- 引入上游代码前，为接入和同步策略建立独立 ADR。
- 工程建立后，把 SDD 链接和结构检查加入自动化质量门禁。
