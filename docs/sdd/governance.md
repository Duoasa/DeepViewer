# SDD Governance

## 适用范围

下列变化需要新建或更新规格：

- 用户可见的功能、交互、默认值或错误行为
- 公共接口、插件契约、持久化数据或跨模块数据流
- 权限、安全、隐私、遥测或凭据处理
- 架构边界、上游集成方式、发布或迁移策略
- 需要多个可独立验证任务才能完成的重构

纯拼写修复、格式调整、无行为变化的机械重构可以豁免，但如果现有文档因此失实，仍需同步更新。

## 编号

- 功能规格：`DV-NNNN-short-name`，例如 `DV-0002-desktop-shell`。
- 架构决策：`ADR-NNNN-short-name.md`。
- 功能需求：`R-NNN`；非功能需求：`NFR-NNN`。
- 验收条件：`AC-NNN`；任务：`T-NNN`。
- 编号一经合并不得复用。删除的提案改为 `Superseded`，不要抹去历史。

## 审批与状态

- `Draft` 和 `Review` 可以自由修改，但不能进入实现。
- 维护者明确认可范围和设计后，规格进入 `Approved`。
- 第一个代码任务开始时进入 `Implementing`。
- 所有验收条件都有通过证据且没有阻断项时进入 `Verified`。
- 对应版本公开发布后进入 `Released`。
- 公开预览版允许关联仍在实施的规格；发布资产必须写入 `releases/`，但不会跳过 `Verified` 的完成定义或自动提升规格状态。
- 实质性范围变化会使原审批失效；状态退回 `Review`，变更部分重新审批。

用户对一个明确功能的直接开发指令可以视为对该目标的认可，但实现方案仍需满足已记录的约束和验收条件。

## 验证职责

- 默认由开发代理完成代码和基础验证，包括静态检查、类型检查、lint、单元/集成测试、生产构建、架构检查、包体结构与校验和验证。
- 默认由项目维护者手动完成视觉和交互验收，包括点击控件、键盘操作、窗口拖动、侧栏切换、全屏切换以及逐页视觉检查；开发代理不得代替维护者操作应用界面。
- 视觉或交互验收条件在基础验证通过后仍记录为 `Pending Manual`，只有维护者明确反馈验收结果后才能记为 `Pass`。
- 存在 `Pending Manual` 验收条件的规格保持 `Implementing`，不得仅凭构建、截图、DOM 几何或自动化脚本提升为 `Verified`。
- 维护者针对某一次任务明确要求代理执行特定交互验证时，可以在该次任务范围内例外，并在 `verification.md` 中记录授权与证据。

## 公开发布安全基线

- 本节适用于 stable、pre-release、公开测试包以及对既有 GitHub Release 资产的替换或重传；任何可通过公开 URL 获取的安装包都不得豁免。
- 每个公开版本的安装资产必须从该版本源代码和固定依赖重新构建；不得复用、改名或重新上传旧版本的 `.app`、DMG、Runtime 或校验清单。
- “全新包”要求重新生成 Runtime、staging、`.app`、DMG 和校验清单；仅重新压缩、复制或改名已有产物不构成全新构建。
- 公开安装资产对个人数据和凭据实行零容忍：不得包含开发者或维护者的个人设置、工作区内容、会话、日志、用户名路径、主目录元数据、API Key、Token、Authorization 值或其他凭据。
- 发布构建必须使用仅含明确允许输入的临时 staging 目录，并在每个架构构建前清理对应 Runtime、staging、应用输出和 DMG。
- 上传前必须对最终 `.app` 的 ASAR、内置 Runtime、资源路径和文本内容执行自动净化审计；审计需检查敏感文件名、开发机绝对路径和当前构建环境中的高置信度凭据值，任何命中都必须阻断发布且不得在日志中打印秘密原文。
- Release 必须发布新生成资产的 SHA-256 清单，并在 SDD 发布记录中保存构建、净化审计、DMG 完整性和远端 digest 核验结果。

## 可追踪性

每条链路必须可从前向后、也可从后向前追踪：

```text
产品目标 → R/NFR → 设计章节 → T → 代码/测试 → AC 验证证据
```

- `design.md` 引用它满足的 `R-*` 和 `NFR-*`。
- `tasks.md` 中每个任务至少引用一个需求、设计章节或验收条件。
- `verification.md` 覆盖全部 `AC-*`，并记录可复现证据。
- 提交或 PR 应引用规格 ID，例如 `DV-0002`。

## 变更控制

实施中发现遗漏时：

1. 暂停受影响的实现切片。
2. 更新问题、需求、设计、风险和验收条件。
3. 如果范围或风险实质变化，将状态退回 `Review`。
4. 重新获得认可后继续实施。
5. 同步更新任务和验证映射。

紧急修复可以先建立最小规格，至少记录问题、风险、修复方案、回滚方法和验收证据；事后再补充完整背景。

## 完成定义

规格进入 `Verified` 前必须满足：

- 所有必需任务已完成或有明确的后续规格承接
- 所有验收条件都有通过证据
- 所有标记为 `Pending Manual` 的视觉或交互验收均已由维护者明确确认
- 相关自动化检查已通过
- 用户可见行为、接口和架构文档已同步
- 安全、隐私、迁移和回滚影响已处理或明确标记为不适用
- 没有未声明的阻断风险

## 文档写作规则

- 描述可观察行为、约束和决策，不记录模型的隐藏推理过程。
- 使用具体术语，避免“以后优化”等不可验证表述。
- 假设、事实和决定必须明确区分。
- 一个事实只保留一个权威位置，其他位置使用链接。
- 文件使用相对链接并保持一个结尾换行。
